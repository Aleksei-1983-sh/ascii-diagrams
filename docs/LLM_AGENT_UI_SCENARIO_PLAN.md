# Анализ сценария LLM <-> ascii-diagrams

## Целевой сценарий

Нужен такой поток работы:

1. Внешний AI-агент получает задачу создать диаграмму.
2. Агент формирует диаграмму в JSON-формате, который понимает `ascii-diagrams`.
3. Агент запускает вашу программу в отдельном терминальном окне.
4. Программа открывает TUI и показывает диаграмму.
5. Пользователь правит диаграмму мышью и клавиатурой.
6. После слов пользователя "я поправил" агент не открывает новое окно, а читает текущее состояние уже открытой программы.
7. Агент при необходимости правит диаграмму и отправляет изменения обратно в уже открытую программу.
8. TUI сразу показывает обновлённую диаграмму.

## Что мешает целевому сценарию прямо сейчас

### 1. В `--agent-ui` нет команды `get_state`

Это главный функциональный разрыв.

В обычном `--agent` есть `get_state`, а в live-мосте `--agent-ui` этой команды нет.

Подтверждение:
- `get_state` есть в [src/agent_api.c](/home/di/projects_С/ascii-diagrams/src/agent_api.c:365)
- `get_state` отсутствует в [src/agent_live_ui.c](/home/di/projects_С/ascii-diagrams/src/agent_live_ui.c:281)

Следствие:
- пользователь может править диаграмму в открытом TUI;
- внешний агент не может потом штатно прочитать актуальное состояние этой же открытой сессии через live-мост.

Без этого пункт "я поправил, посмотри текущее состояние и при необходимости поправь ещё" не закрывается.

### 2. Нет симметричной операции "загрузить полное состояние JSON"

Сейчас есть:
- экспорт всего состояния: `diagram_export_state_json`
- набор атомарных команд для изменения по частям

Но нет:
- `diagram_import_state_json(...)`
- `replace_state`
- `load_state`

Подтверждение:
- экспорт есть в [src/diagram.c](/home/di/projects_С/ascii-diagrams/src/diagram.c:1094)
- в проекте нет импорта JSON состояния: поиск по коду показывает отсутствие такого API

Следствие:
- агент может обновлять диаграмму только серией отдельных команд;
- это возможно, но неудобно и рискованно для синхронизации;
- если LLM сгенерировал новую полную версию диаграммы, применить её одним действием нельзя.

### 3. Нет встроенного launcher-а для открытия в отдельном терминальном окне

Программа умеет работать в `--agent-ui`, но сама по себе не открывает новое окно терминала и не предоставляет helper для внешнего агента.

Подтверждение:
- в коде нет вызовов `xterm`, `gnome-terminal`, `kitty`, `alacritty` и аналогов

Следствие:
- это придётся делать внешнему оркестратору;
- для реального UX нужен либо отдельный скрипт, либо встроенный helper-режим запуска.

### 4. Нет протокола синхронизации "пользователь закончил правки"

Сейчас внешний агент может только:
- послать команду;
- получить ответ;
- вручную по вашему сообщению решить, когда делать `get_state`

Но нет явного события:
- `state_changed`
- `user_edit_finished`
- `version`
- `revision`

Следствие:
- первая версия может жить и без этого;
- но без ревизий и уведомлений легко получить гонки между ручными правками пользователя и новыми правками агента.

### 5. Нет отдельного внешнего SDK/CLI-клиента для live-режима

FIFO-пути печатаются в `stderr`, но готового клиента для общения с live-TUI сейчас нет.

Подтверждение:
- [src/asciiflow.c](/home/di/projects_С/ascii-diagrams/src/asciiflow.c:34)

Следствие:
- интеграция с LLM возможна, но внешнему агенту придётся самому знать:
  - как запускать процесс;
  - где брать FIFO-пути;
  - как писать JSONL;
  - как читать ответы.

## Итоговая оценка

Сценарий **частично уже поддержан архитектурно**, но **не закрыт до конца**.

Что уже реально работает:
- внешний агент может генерировать диаграмму в JSON;
- TUI можно открыть в режиме live bridge;
- агент может отправлять изменения в уже открытую TUI без перезапуска.

Что ещё обязательно нужно сделать:
- добавить чтение текущего состояния из `--agent-ui`;
- добавить удобный механизм применения полного JSON-состояния;
- сделать внешний launcher/client для отдельного терминального окна и работы с FIFO.

Без этих трёх пунктов сценарий будет либо неполным, либо неудобным для реального использования с LLM.

## Рекомендуемый план действий

### Этап 1. Довести live bridge до паритета с `--agent`

1. Добавить в `src/agent_live_ui.c` команду `get_state`.
2. Переиспользовать `diagram_export_state_json(&app_state_get()->diagram, ...)`.
3. Вернуть ответ в том же JSON-формате, что и у `--agent`.
4. Проверить, что внешний процесс может:
   - создать диаграмму;
   - получить state;
   - изменить диаграмму;
   - снова получить state.

Почему это первый шаг:
- это минимальное изменение, которое закрывает основной пробел вашего сценария.

### Этап 2. Вынести общий dispatch команд для `agent_api` и `agent_live_ui`

1. Убрать дублирование логики между `src/agent_api.c` и `src/agent_live_ui.c`.
2. Сделать общий модуль, например:
   - `agent_commands.c`
   - `agent_commands.h`
3. Передавать в него:
   - `Diagram_t *diagram`
   - callback для отправки ответа
   - флаг `running`, если нужен `quit`

Почему это важно:
- сейчас команды продублированы почти полностью;
- если добавить `get_state`, `replace_state`, `load_state`, их придётся поддерживать в двух местах;
- это увеличит риск рассинхронизации API.

### Этап 3. Добавить команду применения полного JSON-состояния

1. Добавить API уровня `diagram`:
   - `int diagram_import_state_json(Diagram_t *diagram, const char *json);`
   или
   - `int diagram_replace_state(Diagram_t *diagram, const DiagramRect_t *rects, ...);`
2. Добавить live/API-команду:
   - `set_state`
   или
   - `replace_state`
3. Семантика команды:
   - полностью очищает текущую диаграмму;
   - валидирует входной JSON;
   - загружает `rects` и `conns`;
   - при ошибке не оставляет диаграмму в полуобновлённом состоянии.
4. Реализовать загрузку через временный `Diagram_t` и swap только после полной валидации.

Почему это важно:
- LLM удобнее работать с полным state, чем собирать diff-команды;
- так проще делать "я посмотрел и пересобрал диаграмму".

### Этап 4. Добавить ревизии состояния

1. Ввести счётчик версии диаграммы, например `state_revision`.
2. Увеличивать его после каждого изменения:
   - mouse edit;
   - keyboard edit;
   - live command;
   - agent command.
3. Возвращать ревизию в ответах `get_state`.
4. Для `set_state`/`update_*` поддержать опциональный параметр:
   - `expected_revision`

Почему это важно:
- это защитит от ситуации, когда пользователь изменил диаграмму после того, как агент уже прочитал старое состояние.

### Этап 5. Сделать внешний launcher для отдельного терминального окна

1. Добавить скрипт, например:
   - `tools/asciiflow_agent_ui_session.sh`
2. Сценарий скрипта:
   - генерирует уникальный `base_path` для FIFO;
   - запускает `./asciiflow_linux --agent-ui <base_path>` в новом терминале;
   - ждёт появления `<base_path>.in` и `<base_path>.out`;
   - возвращает наружу реквизиты сессии.
3. Поддержать популярные терминалы в порядке fallback:
   - `xterm`
   - `gnome-terminal`
   - `kitty`
   - `konsole`
4. Формат результата скрипта лучше сделать JSON, например:
   - `{"pid":..., "base_path":"...", "in_fifo":"...", "out_fifo":"..."}`

Почему это важно:
- внешний LLM-оркестратор должен открывать вашу TUI без ручных действий.

### Этап 6. Сделать простой live-клиент для LLM-оркестратора

1. Добавить минимальный CLI-клиент, например:
   - `tools/asciiflow_live_client.py`
   или
   - `tools/asciiflow_live_client.sh`
2. Команды клиента:
   - `send <jsonl>`
   - `get-state`
   - `set-state <file>`
   - `clear`
   - `render-ascii`
3. Клиент должен:
   - писать JSONL в input FIFO;
   - читать ровно один ответ из output FIFO;
   - уметь таймауты и понятные ошибки.

Почему это важно:
- это будет реальная точка интеграции для LLM, а не набор ручных действий с FIFO.

### Этап 7. Добавить режим "человек поправил, агент перечитай"

1. Базовая версия:
   - пользователь вручную говорит агенту "я закончил";
   - агент вызывает `get_state` у уже открытой live-сессии.
2. Улучшенная версия:
   - добавить команду/флаг в UI или file marker для сигнала "готово к повторному анализу".
3. Опционально:
   - добавить авто-экспорт последнего state в файл около FIFO.

Почему это важно:
- это ровно ваш целевой UX после ручной правки.

### Этап 8. Добавить документацию именно под этот workflow

1. В `README.md` описать отдельный раздел:
   - "LLM live editing workflow"
2. Дать пример полного цикла:
   - старт live UI;
   - initial `set_state`;
   - ручная правка;
   - `get_state`;
   - повторный `set_state` или patch-команды.
3. Зафиксировать контракт JSON-формата state.

## Практический MVP

Если делать минимально необходимую версию без лишней архитектуры, то порядок такой:

1. Добавить `get_state` в `agent_live_ui`.
2. Добавить внешний launcher, который открывает `--agent-ui` в новом терминале.
3. Добавить простой live-клиент для FIFO.
4. На стороне внешнего агента использовать текущий JSON state как основной формат обмена.
5. Только после этого добавлять `set_state` и ревизии.

Такой MVP уже позволит:
- агенту создать диаграмму;
- открыть её в отдельном окне;
- пользователю вручную поправить её;
- агенту перечитать текущее состояние той же сессии;
- агенту внести новые правки в уже открытое окно.

## Приоритет изменений

### Критично

1. `get_state` для `--agent-ui`
2. launcher нового терминала
3. live-клиент для FIFO

### Очень желательно

1. `set_state` / `replace_state`
2. общий dispatch для двух agent-режимов

### Следующий уровень надёжности

1. `state_revision`
2. защита от гонок
3. уведомления о пользовательских правках

## Вывод

Проект уже находится близко к нужному сценарию, потому что:
- JSON API уже есть;
- live TUI bridge уже есть;
- экспорт состояния уже есть.

Основной недостающий кусок сейчас: `--agent-ui` умеет принимать изменения, но не умеет полноценно отдавать текущее состояние обратно внешнему агенту. После закрытия этого пробела и добавления простого launcher/client ваш сценарий станет реализуемым без смены общей архитектуры проекта.
